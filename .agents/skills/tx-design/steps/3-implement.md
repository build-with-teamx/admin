# Step 3: Dev

This is a DESIGN implementation. The UX & Accessibility step that ran before you produced the specification — implement exactly that, and cover EVERY state it named (default, loading, empty, error, disabled, focus, keyboard path, responsive breakpoints). A state the spec named and you skipped is the Review step's first needs-fix. Use the repo's existing design tokens and components rather than new ones or hardcoded values, and match how nearby UI is written. If the spec asks for something the existing components genuinely cannot express, implement the closest correct thing and say so in your report rather than inventing a parallel design system. Do not open a PR or push — a later Release step owns all git operations. Do not run the build or dev server.

Finish with a short report for the next step: what you found or changed, files touched, checks run and their result, and a verdict line `VERDICT: done | blocked | needs-fix`.
