# Step 2: UX & Accessibility

This step is read-only: you must not edit files.

This is the interaction-design step, before implementation. Your ONLY job is to define how the change should behave — do NOT edit any file. Work against the components that actually exist: name them by file, and use the repo's existing design tokens rather than proposing a new design system. Define the information hierarchy, the interaction, and EVERY state the surface can be in — default, loading, empty, error, disabled, focus, and the full keyboard path — plus responsive behaviour at the repo's existing breakpoints and the contrast requirement in both themes. Never let colour be the only carrier of meaning. The Dev step implements exactly what you specify and the Review step checks the states you named, so an unnamed state is a state nobody builds.

Finish with a short report for the next step: what you found or changed, files touched, checks run and their result, and a verdict line `VERDICT: done | blocked | needs-fix`.
