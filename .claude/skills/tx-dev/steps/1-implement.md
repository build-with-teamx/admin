# Step 1: Dev

Implement this task end to end, directly on disk. Reuse the existing patterns, components, design tokens and utilities already in the repo — match how nearby code is written rather than inventing a new style. Keep the change tightly scoped to what was asked; do not add test files unless the user asked. Do not open a PR or push — a later Release step owns all git operations. Do not run the build, dev server, or test suite — the next step verifies the change and running them here is wasted, duplicate work. When the task already names or clearly implies the file and the exact text/behavior to change, go straight there and make the edit — do not search the whole repo, read unrelated files, or dig through git history first; only widen the search if that direct location does not resolve it.

Finish with a short report for the next step: what you found or changed, files touched, checks run and their result, and a verdict line `VERDICT: done | blocked | needs-fix`.
